# 에이전트 검증소 (Agent Verifier)

AI 에이전트가 "이게 최저가예요", "사실이에요", "완료했어요" 라고 말할 때, 그 말을 **위험도에 맞는 깊이로 검증하고 서명된 영수증**을 발행합니다.

- **과정 판정** (행동 직전 게이트): 결제·발송 같은 되돌리기 어려운 행동 전에 주장 + 작업 기록을 보고 `진행 | 정지(사람에게)`.
- **사후 판정** (결과 영수증): 작업 뒤 결과를 검증해 영수증 발행 → 원장에 쌓여 에이전트별 정확도(평판).
- 검증소는 작업을 대신하지 않습니다 — 수행은 에이전트, 판정은 검증소.

## 실행

검토용 기본 경로는 가상 공급자입니다. 대회 운영진이 승인된 Liner 키를 별도로 주입한 경우에만, 아래 실행 환경에서 `VERIFIER_PROVIDER=mock`을 `VERIFIER_PROVIDER=liner`로 바꾸어 실제 조회를 평가할 수 있습니다. `LINER_API_KEY`는 스태프가 환경 변수로 주입하며 ZIP이나 로그에 포함하지 않습니다. 실조회는 비용이 발생할 수 있습니다.

Node.js 20+ 만 필요합니다 (외부 패키지 0). 준비 확인이 필요하면 `cd verifier`에서 `npm install --offline --ignore-scripts --no-audit --no-fund`를 선택적으로 실행할 수 있습니다.

```bash
cd verifier
VERIFIER_NO_DOTENV=1 VERIFIER_PROVIDER=mock npm test # 동봉 소스 테스트
VERIFIER_NO_DOTENV=1 VERIFIER_PROVIDER=mock npm run demo # 가상 데이터 시연
VERIFIER_NO_DOTENV=1 VERIFIER_PROVIDER=mock node bin/verifier.mjs price "예시 문구" 900 --phase outcome
```

`.env` 를 읽지 않게 하려면 `VERIFIER_NO_DOTENV=1`(정확히 `1` 일 때만 — `true`·`yes` 는 무시됩니다).

### MCP 서버로 붙이기

```json
{ "mcpServers": { "verifier": { "command": "node", "args": ["/path/to/verifier/mcp/server.mjs"], "env": { "LINER_API_KEY": "..." } } } }
```

도구: `verify_price` · `verify_claim` · `court_claim` · `verify_done` · `check_receipt` · `agent_reputation` · `verifier_usage`

결제 측은 `verify_price` 에 1회용 `request_nonce`(문자열)를 넣고, 받은 영수증을 `check_receipt` 에 **자기가 결제하려는 내용**(`expected_nonce` · `expected_item` · `expected_price_krw` · `expected_seller_url`)과 함께 넣습니다. **결제를 실행해도 되는지는 `authorizes` 한 필드로만 판단합니다** — `valid` 는 "서명·발급자·다이제스트·만료·nonce 가 맞는 진짜 영수증"이라는 뜻일 뿐이라 정지·사후 영수증도 `valid: true` 입니다. `authorizes` 는 아래가 **모두** 맞을 때만 `true` 이고, 막은 사유는 `not_authorized` 에 나옵니다.

- `valid` · 과정(process) 영수증 · 판정 `proceed` · 가격 영수증(사실 주장 영수증은 결제 허가가 아님)
- `expected_nonce` 를 줬고 영수증의 nonce 와 같음 — 주지 않으면 `false`
- 기대 상품·금액·판매처를 줬고 영수증의 주장과 같음 — 쉬운 다른 주장으로 받은 영수증이 이 결제의 허가가 되지 않게
- 실조회 공급자(`liner`)의 판정 — mock·mock-fallback 판정은 유효한 영수증이어도 허가가 아님(시연에서만 `VERIFIER_AUTHORIZE_PROVIDERS=liner,mock` 으로 넓힘)

`request_nonce` 는 과정 판정에 한 번만 쓸 수 있습니다(정지 뒤 같은 결제 건으로 다시 물으면 거절, 원장으로 기억). 공급자 오류로 정지한 건도 같은 값으로는 다시 물을 수 없으니, 재시도는 결제 측에서 새 값을 받아서 합니다. 영수증의 재사용(같은 영수증을 두 번 제시)을 막는 것은 결제 측 몫입니다. CLI: `price … --nonce N` · `check 영수증.json --nonce N --item "<상품>" --price <원> --seller URL` → `{valid, reasons, authorizes, not_authorized}`. 문자열이 아닌 nonce, 다른 플래그로 시작하는 플래그 값(`--nonce --json`)은 오류로 거절합니다.

## 위험도 3단

| 단계 | 언제 (src/tiers.mjs) | 검증 깊이 |
|---|---|---|
| low | 50만원 미만·되돌릴 수 있음 | 즉시 조회 (Liner web, 없으면 quick) |
| mid | 50만원+ · 되돌릴 수 없음 · 사실/완료 주장 | 근거 대조 `claim`: Liner AI 검색(+논문) → 판사 1명, 채택 + 독립 출처 2곳 이상일 때만 확인 |
| high | 300만원+ · 되돌릴 수 없는 100만원+ · 의료/법률/금융 · **의뢰자 정책이 없는 사실 주장** | 법정 `court`: 검사(반증)·변호(근거) Deep Research → gpt·claude 계열 판사 2명 → 두 조사 모두 성공 + 둘 다 채택 + 각 판사가 실제 변호 출처를 1개 이상 인용 + 인용된 변호 출처 합집합의 독립 호스트 2곳 이상일 때만 진행 (가격 주장의 high 는 아직 과정·사후 모두 확인불가) |

### 사실 주장의 위험도 — 누가 정하는가 (신뢰 경계, tiers-v4)

- **정하는 쪽은 의뢰자**(검증소를 띄우는 운영자)입니다: `createVerifier({ policy: { claim_domain } })`, MCP 서버·CLI 는 환경변수 `VERIFIER_POLICY`(JSON 파일 경로, 예 `{"claim_domain":"general"}`). 값은 `general | medical | legal | finance` 중 하나이고, 그 밖의 값이나 읽을 수 없는 파일은 기동을 거절합니다(오타가 조용히 다른 등급이 되지 않게).
- **검증받는 에이전트**가 넘기는 `domain`·위험도 override 는 **올리기만** 됩니다. 의뢰자가 medical 로 정했으면 에이전트가 `other`·`low` 라고 해도 법정입니다.
- **의뢰자 정책이 없으면 사실 주장은 전부 high(법정)** 입니다(fail-safe). 주장문 낱말로 의료·법률을 추정하던 규칙은 없앴습니다 — 낱말 열거로는 닫을 수 없어서(리뷰 재현 10건 중 9건 미탐).
- MCP·CLI 는 에이전트가 준 domain 이 알아볼 수 없는 값이면 입력 오류로 돌려줍니다(조용히 mid 로 두지도, 조용히 법정으로 올리지도 않음).
- 에이전트 domain 문자열은 NFKC 정규화 → 문자·숫자 외(폭 0 공백·구두점) 제거 → 별칭(med·pharma·의료·건강·법률·세금 등) 매칭, 고위험 별칭을 포함만 해도('의료 건강') 올립니다.
- 영수증 `method.domain_source` 가 등급의 출처를 남깁니다: `policy`(의뢰자 지정) · `agent_raise`(에이전트가 올림) · `default_high`(정책 없음 기본값).

mid 사실 주장의 확인은 판사가 근거로 든 출처 중 **실제로 제공된 출처**의 독립 호스트가 2곳 이상일 때만, 반박도 판사가 실제 제공된 출처를 1건 이상 인용했을 때만입니다(아니면 확인불가). 판사 프롬프트는 주장문·보고서를 JSON 문자열로만 넣고 그 안의 지시는 무시하라고 명시합니다.

## 영수증

`verifier-receipt/0.1` — JCS(RFC 8785) 정규화 + Ed25519 JWS detached 서명. 필드: `phase`(process|outcome) · `tier` · `subject.claim_digest` · `verdict{result, decision, reasons, better_offer, review_candidates?}` · `evidence[]` · `cost{usd, calls}` · `method`.
검증: 서명 · 발급자 신뢰 목록 · 주장 다이제스트 일치 · 만료 · nonce → `valid`. 결제 허가는 `authorizes`(valid + process + proceed + 가격 영수증 + nonce·기대 주장 일치 + 실조회 공급자).

## 기존 자산과 대회 기간 기여

## 알려진 한계

**먼저 읽을 것 — 평문 문구의 조건 표시는 다 잡지 못합니다.** 격리 리뷰를 11회 받았고 마지막 리뷰(11차)도 승인이 아니라 수정 요청으로 끝났습니다. 마크업·인코딩으로 글을 숨기는 경로는 허용 목록(price-v9)으로 닫았지만, 아래는 고치지 않고 남겼습니다. 이 경우 조건부·중고 가격이 "확인"되어 진행(결제 허가)까지 갈 수 있습니다.
- 조건 표시(카드·쿠폰·할인 등)는 가격 앞 16자·뒤 12자 안에서만 찾습니다. "299,000원 (삼성 현대 KB국민 신한 등 일부 카드 결제 시)"처럼 멀리 있으면 놓칩니다. 가격은 본문에, 조건은 제목에 있는 경우도 놓칩니다.
- 조건·상품 상태 낱말은 목록에 있는 한국어 표현만 봅니다. "최대 혜택가"·"회원 전용"·"첫구매"·"오픈박스"·"단순개봉"·"S급", 영문 "used"·"refurbished"·"coupon"은 표시가 붙지 않습니다.
- 범위는 `~` 만 봅니다. "299,000원 - 359,000원"·"₩299,000 – ₩359,000"의 앞 값은 표시 없는 가격으로 읽힙니다.
- 단위 없이 문장부호로 갈린 더 싼 값("판매가 259·000", "259, 000")과 영문 O 로 쓴 0("259,OOO원")은 읽지 못합니다.
- 2차 검색 출처의 제목 판정도 낱말 목록입니다. "case"·"cover", "케-이스"처럼 쓴 부속품 글을 같은 상품으로 칩니다.
- 글 전체에서 조건 낱말을 찾게 바꾸면 첫 항목은 닫히지만 표본 데모조차 진행이 0건이 되어(전부 정지) 채택하지 않았습니다. 이 게이트는 "사람 확인을 줄이는 1차 필터"이지 조건부 가격을 완전히 걸러내는 장치가 아닙니다.

- 상품 동일성: 검색 결과의 가격이 같은 모델·옵션인지 아직 판별하지 않습니다 (예: 변형 모델이 더 싸게 잡힐 수 있음).
- 가격 추출은 요약문 텍스트 기반입니다. 추출 단계는 **어떤 값도 버리지 않고** 문맥 표시(조건부·차액·기준액·근사·중고 등)만 붙이며, 판정은 한 곳(`classify`)에서만 합니다. 주장가보다 싼 값은 표시·크기와 무관하게 전부 정지 사유입니다. 그래서 추출 잡음은 진행이 아니라 정지(사람 확인) 쪽으로 실패합니다.
- 읽지 못한 숫자(전각·`won`·단위 없는 `259,000`·`25만9천`·`259k`·한글 수사 등)도 버리지 않고 `unparsed` 표시 관측으로 남깁니다. 주장가보다 작게 읽히면 정지 사유이고, 주장가와 같아도 확인 근거가 아닙니다. 그래서 리뷰 수·전화번호·용량 같은 가격 아닌 숫자("리뷰 1,234건"·"1588-1234"·"4K")도 주장가보다 작으면 정지합니다. 판정부가 가격이 아닌 것으로 보는 예외는 둘뿐입니다(추출 단계는 둘 다 버리지 않고 관측으로 남깁니다): 상품명에 들어 있는 숫자("LG 그램 2024"의 2024), 그리고 쉼표·원 없는 19xx·20xx 네 자리 숫자가 **주장가의 5% 미만**일 때(연도로 봄. 문맥은 보지 않으므로 4만 원 넘는 주장에서는 "최저 1999"·"행사가 1990" 처럼 단위 없이 적힌 2천 원 안팎 값도 연도로 넘어갑니다 — `원`·`won` 이 붙으면 가격으로 읽습니다 — 주장가가 약 4만 원보다 낮은 상품에서는 예외가 없어 날짜가 섞이면 정지).
- **평문이 아닌 글이 조회 결과에 있으면 진행하지 않습니다**(`nonplain_text_in_results`, price-v9): 제목·본문·LLM 답이 전부 허용 글자(한글·영문·숫자·공백과 `, . ( ) [ ] - : ; / · ~ + | ! ? ' " # * = _ @ ₩ % …` 등 흔한 문장부호)로만 되어 있을 때만 확인합니다. 꺾쇠·`&`·`\\`·`%3C` 꼴·폭 0 글자·전각 글자·한자·이모지·그 밖의 기호가 하나라도 있으면 정지합니다. 글을 쪼개고 숨기는 인코딩을 하나씩 막는 방식이 리뷰 10회 동안 닫히지 않아, 막을 것을 열거하는 대신 허용할 것을 정했습니다. 대가: `<b>` 강조·"홈 > 가전"·"AT&T"·™·이모지가 든 정상 결과도 정지하므로 **실데이터에서는 진행이 드뭅니다**. 모양만 같은 다른 문자(키릴 О 등)·보이지 않는 글자(LRM·폭 0 등)·결합 문자도 목록 밖이라 정지합니다. 평문이 아닌 글에서 읽은 값은 확인 근거도 사후 반박 근거도 되지 못하고(더 싸면 차단만), 그런 제목은 같은 상품으로 치지 않습니다.
- HTML 이 섞인 글은 여러 가지로 읽어 합칩니다(아무 글자도 지우지 않은 글 / 태그를 공백으로 바꾼 글 / 태그를 지우고 앞뒤를 붙인 글 / `<…>` 를 통째로 지운 글 / 남은 꺾쇠 글자만 지운 글). 꺾쇠가 아닌 글자로 표시 낱말을 쪼갠 글("카.드.할.인")은 잡지 못합니다. 어느 쪽에서든 읽힌 값은 남고, 어느 쪽에서든 붙은 조건부·범위 표시는 그 값 전체에 붙습니다.
- 대가로 정지가 매우 잦습니다. 실데이터 요약문에는 배송비·옵션가로 보이는 작은 값('4,000원')이나 카드 할인가가 거의 늘 섞여 있어, 2026-11-22 실데이터 기준 다나와 '최저 287,490원' 주장도 정지합니다(같은 옵션인지·실제 결제가인지는 사람 몫). 오프라인 mock 표본은 진행 시연을 위해 그런 값을 뺐습니다.
- 표시가 없는 싼 값만 '최저' 표시가 붙었을 때 반박(더 나은 값 제시)이 되고, 나머지는 확인불가입니다. 반박이든 확인불가든 과정 판정은 정지입니다.
- 같은 플랫폼 안에서 경로만 다른 판매처(storeA·storeB)는 같은 판매처로 봅니다(리뷰 M3, 미처리). 이 한계는 '주장 판매처에서 관측' 조건과 `authorizes` 의 판매처 대조에도 그대로 적용됩니다 — 같은 오픈마켓의 다른 상점은 구별하지 못합니다.
- `request_nonce` 1회용은 원장으로 기억합니다. 원장 없이 띄우면 재기동 뒤 같은 값을 다시 쓸 수 있고, 같은 원장을 쓰는 두 프로세스가 같은 순간에 같은 값을 받으면 둘 다 통과할 수 있습니다.
- 독립 출처 수는 판매처·기관 단위 호스트로 셉니다. 2단 접미사는 자주 나오는 것만 압니다(co.kr·ac.uk·go.jp 등) — 목록 밖(github.io 하위 사이트 등)은 한 곳으로 접혀 정지 쪽으로 틀립니다.
- 판사 계열(gpt·claude)은 호출 경로 라벨로만 보장됩니다 — 라우터가 실제로 같은 모델을 쓰면 확인할 수 없습니다(리뷰 M4, 미처리).
- 2차 검색(가격으로 찾기) 결과는 제목에 상품명 낱말이 전부 있고(모델 번호는 독립 토큰으로) 부속품 낱말(케이스 등)이 없어야 출처로 셉니다. 그래도 상품명이 더 긴 다른 상품("갤럭시 버즈 프로 3" ↔ "프로 3")은 구별하지 못합니다.
- 작업 기록(tool_calls)과 가격 주장의 '되돌릴 수 있음'(reversible, 기본 true)은 에이전트의 자기 신고입니다(리뷰 r5 M2, 미처리 — 운영에서는 의뢰자 정책으로 옮겨야 함).
- stdio 로 붙이면 서명 키(`.keys/`)와 원장(`data/`)이 에이전트와 같은 OS 사용자의 파일입니다. 에이전트가 파일을 읽을 수 있으면 영수증을 위조할 수 있으므로, 운영에서는 검증소를 다른 사용자·다른 기기에서 띄워야 합니다(리뷰 r5 M7).
- 호출 수 상한·하루 비용 상한은 서버에 없습니다(법정 1건 약 $0.45). 운영에서는 의뢰자 쪽에서 호출을 제한해야 합니다(리뷰 r5 M6, 미처리).
- 평판 원장의 `agent_id` 도 자기 신고입니다. 남이 다른 에이전트의 id 로 영수증을 받으면 그 에이전트의 평판에 섞입니다(사칭) — 신원 증명(서명된 에이전트 키 등)에 묶는 것은 아직 없습니다. 같은 영수증의 중복 줄은 한 번만 세고, 정확도는 사후(outcome) 영수증으로만 계산하며, 같은 주장(request_nonce 를 뺀 주장 내용)의 사후 영수증은 에이전트별 1건만 셉니다 — 반박이 한 번이라도 있으면 그 반박을, 없으면 최신 1건을(재검증으로 감점을 지우지 못하게). 완료(done) 영수증은 반박이 나올 수 없는 규칙이라 정확도에 넣지 않고 `done` 칸에 건수만 셉니다(rep-v6). 완료 영수증은 영수증 수·확인·반박·정지 수에도 넣지 않습니다. `accuracy_by_type.claim` 은 근거 대조(mid)와 법정(high)을 합친 값입니다. 전체 정확도는 쉬운 주장을 섞어 희석할 수 있으므로, 주장 종류별 정확도(`accuracy_by_type`: price·claim)를 함께 냅니다 — 결제 권한을 줄 때는 price 칸을 보세요. 다만 주장 내용을 조금씩 바꾸면(판매처 URL 등) 다른 주장으로 세어 정확도 부풀리기를 완전히 막지는 못합니다. `agent_reputation` 은 MCP 클라이언트 누구나 조회할 수 있습니다.
- 완료 주장(done-v3, `verify_done` · CLI `done "<제목>" <URL>` — http/https 기본 포트 URL 만 받음)은 "그 URL 이 공개 웹에 있고 제목이 과업을 가리킨다"까지만 봅니다 — **남이 이미 만든 페이지**를 자기 산출물이라고 내밀면 구별하지 못합니다.
- Liner 호출에는 시간 제한이 있습니다(검색·판사 30초, AI 검색 120초, Deep Research 900초, env `LINER_TIMEOUT_MS` 로 전체 덮어쓰기). 넘으면 공급자 오류로 정지 영수증이 남습니다. 값이 양의 정수가 아니면 기동을 거절하고, 한 값이 Deep Research 까지 덮으므로 짧게 주면 법정은 항상 정지합니다.
- `VERIFIER_PROVIDER=liner` 인데 `LINER_API_KEY` 가 없으면 경고를 내고 `mock-fallback` 공급자로 돕니다. 영수증 `provider` 에 그 이름이 남으므로 실데이터 판정과 섞이지 않게 걸러 볼 수 있습니다.

## 판정 규칙 (price-v9)

확인은 "더 싼 값을 못 찾음"이 아니라 **긍정 증거**가 있을 때만 냅니다. 추출은 값을 버리지 않고 표시만 붙이고, 아래 판정은 `src/verify/price.mjs` 의 `classify` 한 곳에서만 합니다.

1. 주장가가 **문맥 표시 없이** 실제로 관측됨 — 주장가 이상 주장가×1.01 이하(허용오차는 위쪽에만). 할인·카드·쿠폰 같은 조건부(숫자 앞 16자·뒤 12자 안에서만 찾음: "299,000원 (카드 할인 적용 시)"), '차이·차액·절약' 뒤의 차액, '이상·이하·부터' 앞의 기준액("30만원 이상 구매시"), 범위(`~`), '원대' 근사값, 중고·리퍼·렌탈 결과의 값은 주장가와 같아도 확인 근거가 아닙니다.
2. 그 관측의 웹 출처 ≥ 2 (판매처 단위. LLM 답은 출처로 세지 않고 차단에만 씀). 모자라면 같은 가격으로 웹 검색 1회 추가 — 이 2차 검색 결과는 제목이 상품을 가리켜야(상품명 첫 낱말 + 낱말 절반 이상) 출처가 되고, 아니면 다른 상품 표시(off_item)가 붙습니다.
3. 주장가 **미만**의 관측이 **하나도** 없음 — 1원 차이라도, 예외 없음. 웹 출처의 표시 없는 '최저' 값이면 **반박**(더 나은 값 제시), 나머지(LLM 답만의 '최저' 값·표시 없는 값·표시 붙은 값·주장가 30% 미만의 값)는 **확인불가**. 카드 할인가 같은 조건부 최저가는 반박이 아니라 확인불가입니다.
4. 정지·확인불가 영수증에는 사람이 볼 **확인 후보**(`verdict.review_candidates`, 주장가 이하 관측 최대 5곳 — 판매처마다 가장 싼 값 먼저, 주장가 절반 이상 범위의 최솟값은 반드시 포함, 싼 순 표시, `{price_krw, url, source, marks, anchored, snippet}` — snippet 은 값이 나온 필드 원문 80자 이내)를 붙이고 요약에 `확인할 후보 N곳 · 최저 X원(판매처, 표시)` 한 줄을 냅니다. 후보는 판정이 끝난 뒤 만드는 표시 전용이라 결과·결정·사유에 영향이 없습니다(테스트로 고정).

5. 위쪽 허용오차로 확인된 관측값이 주장가보다 높은 위험도 구간에 있으면 확인하지 않습니다(`observed_price_in_higher_tier`) — 주장가를 1% 낮춰 적어 얕은 검증으로 내려가지 못하게.

과정 판정의 진행 조건은 여기에 더해 판매처 URL 명시(형식 검사)·작업 기록상 판매처 2곳 이상·주장 판매처를 실제로 봤을 것·**검증소의 관측에서 주장 판매처가 주장가로 보였을 것**(`seller_price_not_observed` · `seller_price_higher`). 공급자 오류도 정지 영수증으로 남습니다. 과정 영수증은 15분, 사후 영수증은 1년 뒤 만료됩니다.

이 검토용 스냅샷에는 환경 파일, 원장과 벤치마크 데이터 또는 내부 작업 문서를 포함하지 않습니다. 외부 공개용 출처·라이선스 검토는 별도입니다.
